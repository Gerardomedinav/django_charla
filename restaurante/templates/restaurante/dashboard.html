Los 3 Pilares de la Seguridad en Django

Reglas obligatorias para blindar el núcleo de tu aplicación contra exploits e intrusiones

🔑 1. SECRET_KEY

Es la llave maestra para firmar criptográficamente cookies de sesión, tokens de reseteo de clave y firmas CSRF. Debe vivir siempre en el archivo .env y nunca commitearse en Git.

🛑 2. DEBUG = False

En producción, DEBUG=True es un agujero de seguridad crítico porque expone trazas de código, passwords y variables de entorno. En producción siempre DEBUG=False.

📄 3. .env en .gitignore

Tu archivo .env contiene credenciales reales. En el repositorio público únicamente compartimos .env.example como plantilla para el equipo.

Guía de Inicio: Instalar Django y Crear Proyecto

Comandos directos listos para copiar y arrancar un nuevo proyecto con la última versión de Django

[ PYTHON 3.12 + DJANGO 5.1 ]
🐧

Linux (Ubuntu / Debian / WSL)

[ Bash / Zsh ]

Pasos para preparar entorno, instalar la última versión y generar el proyecto:

1. Entorno Virtual
> python3 -m venv .venv && source .venv/bin/activate
2. Descargar Última Versión de Django
> pip install --upgrade pip && pip install django
3. Crear Proyecto Nuevo
> django-admin startproject mi_proyecto .
4. Migraciones y Arrancar Servidor
> python manage.py migrate && python manage.py runserver

1. Capa de Datos: La Despensa (models.py)

Modelos relacionales traducidos a tablas SQL mediante el ORM de Django

models.Model
class Menu(models.Model) Entidad Menú

Representa los ingredientes y platos disponibles en la carta de Little Lemon / El Restaurante de Django.

nombre: CharField(max_length=120) ➔ Nombre del plato o bebida.

tipo: CharField con TIPO_CHOICES ➔ 'PLATO' o 'BEBIDA'.

precio: DecimalField(8, 2) ➔ ¿Por qué Decimal y no Float? Evita errores de redondeo de punto flotante en dinero.

disponible: BooleanField(default=True) ➔ Control de stock.

def __str__(self): Retorna f"{self.icono} {self.nombre} - ${self.precio}" para visualización limpia en el panel de administración y consola.

class Pedido(models.Model) Entidad Comanda

Representa la comanda viva que viaja entre el Mozo (Template) y el Cocinero (Vista).

plato / bebida: ForeignKey(Menu, on_delete=SET_NULL, limit_choices_to=...) ➔ Integridad referencial: si se borra un plato, la comanda no explota sino que queda nula.

estado: PENDIENTE ➔ PREPARANDO ➔ SERVIDO.

def avanzar_estado(self): Máquina de estados finita que avanza la orden automáticamente y ejecuta self.save() en PostgreSQL.

2. Capa de Aplicación: El Cocinero (views.py)

El cerebro operativo que procesa peticiones HTTP, consulta la BD y retorna respuestas

HttpRequest ➔ HttpResponse
def dashboard(request) GET /

¿Para qué sirve? Es la vista principal que prepara la mesa para el comensal.

  • Recibe el objeto request (instancia de HttpRequest).
  • Consulta la despensa con Menu.objects.filter(disponible=True).
  • Usa select_related('plato', 'bebida') para hacer un SQL JOIN en una sola consulta y evitar el problema de rendimiento N+1.
  • Arma la Bandeja del Contexto: un Diccionario de Python (context = {'platos': ..., 'pedidos_pendientes': ...}).
  • Retorna render(request, 'dashboard.html', context) entregando un HttpResponse con código 200 OK.
def tomar_pedido(request) POST /tomar-pedido/

¿Para qué sirve? Registra una nueva orden en el sistema.

  • Es polimórfica: procesa tanto peticiones asíncronas modernas (application/json vía fetch) como envíos tradicionales de formulario HTML.
  • Valida que el nombre del cliente no esté vacío y sanitiza el número de mesa con int(mesa).
  • Crea el registro de base de datos en una sola operación atómica con Pedido.objects.create(...).
  • Retorna un JsonResponse con los datos del pedido recién horneado para que el frontend lo dibuje al instante sin recargar.
def cambiar_estado_pedido(...) POST /cambiar-estado-pedido/<id>/

¿Para qué sirve? Hace fluir el pedido en la cocina (Pendiente ➔ Cocinando ➔ Servido).

  • Usa get_object_or_404(Pedido, id=pedido_id): si el pedido no existe, arroja un HTTP 404 limpio en vez de un error 500 fatal.
  • Ejecuta el método encapsulado pedido.avanzar_estado().
  • Devuelve JsonResponse({'success': True, 'nuevo_estado': ...}) para mover la tarjeta en el tablero Kanban.
def api_pedidos(request) GET /api/pedidos/

¿Para qué sirve? Micro-API REST que serializa los pedidos a formato JSON.

  • Consulta todas las comandas optimizadas con select_related.
  • Transforma el QuerySet de Python a una lista de diccionarios estándar con emojis, mesas y horas formateadas.
  • Alimenta la reactividad del tablero Kanban sin necesidad de instalar dependencias de terceros.
def api_chatbot(request) POST /api/chatbot/

¿Para qué sirve? El puente HTTP hacia el motor semántico de "El Sensei Formoseño".

  • Parsea el payload JSON {'mensaje': '...'}.
  • Delega la consulta a SenseiFormoseno.responder(mensaje).
  • Retorna la respuesta enriquecida con Markdown y calidez formoseña en milisegundos.
def api_terminal(request) POST /api/terminal/

¿Para qué sirve? Emulador Bash educativo para los 4 desafíos interactivos.

  • Valida comandos como makemigrations, migrate, docker compose up -d y seed_data.
  • Soporta comandos auxiliares reales (help, status, clear, ls, pwd, whoami).
  • Controla la progresión de las misiones y entrega feedback pedagógico en vivo.

3. Tablero de Control & CLI (settings.py & seed_data.py)

Arquitectura de infraestructura y herramientas de línea de comandos

manage.py CLI
def can_resolve_host(host) config/settings.py

¿Por qué existe esta función? Permite la auto-detección inteligente de base de datos.

Usa socket.gethostbyname(host) para comprobar si el contenedor de PostgreSQL (db) está accesible. Si corre dentro de Docker, conecta a PostgreSQL; si corre en el host sin Docker, conmuta automáticamente a SQLite sin lanzar un error fatal.

Command.handle(self, *args, **options) commands/seed_data.py

¿Por qué usamos update_or_create y no create? Principio de Idempotencia.

Si el usuario ejecuta python manage.py seed_data diez veces seguidas, update_or_create actualiza los registros sin duplicar empanadas formoseñas ni surubís en la base de datos.

🎯 Simulacro de Preguntas Difíciles del Auditorio (Q&A):

1. ¿Django vs Laravel si ambos son full-stack?

Laravel (PHP) usa MVC tradicional. Django usa MVT sobre Python, lo que otorga una ventaja estratégica insuperable si tu backend necesita conectarse con IA, además de incluir un panel de administración profesional de fábrica.

2. ¿Vistas asíncronas con async def?

En Django 4.1 y 5+, async def permite manejar I/O bound (APIs externas, Azure Storage) sin bloquear el hilo del servidor, aumentando la concurrencia masiva.

3. ¿Es seguro el ORM para transacciones financieras?

Sí. Al usar DecimalField se erradican los errores de punto flotante de FloatField, y con transaction.atomic se garantiza consistencia ACID.

4. ¿Cuándo desacoplar Django con React?

Cuando tenés múltiples clientes (Web React, App móvil Flutter). Con Django REST Framework (DRF) y Swagger (drf-spectacular) creás el contrato OpenAPI perfecto.
